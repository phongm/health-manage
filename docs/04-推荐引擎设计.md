# 04 · 推荐引擎设计

这是本产品的核心。整个引擎是**确定性的规则与打分系统**，不使用大模型做判断。

## 0. 设计原则

1. **零历史数据也必须可用。** 推荐质量随数据积累而提升，但绝不以数据积累为前置条件。
2. **每条推荐都必须能解释。** 输出必须包含"为什么推荐它"，并可追溯到具体的数值缺口或规则。
3. **AI 不参与判断。** 大模型只负责把用户的自然语言输入翻译成结构化数据。所有营养判断、阈值比较、食物取舍由本引擎完成。
4. **安全边界优先级最高。** 任何情况下不得输出低于安全下限的能量方案。
5. **换一换后仍须满足营养目标。** 替换在"营养生态位"内进行，不是随机换一个。

## 1. 整体流程

```
输入：user_id, meal_type, scene, date
  │
  ├─ Layer 0  目标计算        → 每日目标热量与营养目标
  ├─ Layer 1  缺口计算        → 本餐可用额度与营养缺口
  ├─ Layer 2  硬约束过滤      → 排除不可推荐的食物（过敏/忌口/避雷 exclude）
  ├─ Layer 3  候选召回        → 按场景/餐次/角色召回候选池
  ├─ Layer 4  单品打分        → 多因子加权打分
  ├─ Layer 5  组合生成        → 按角色组装成一餐，校验总额度
  ├─ Layer 6  份量微调        → 调整克数使总热量落入额度区间
  └─ Layer 7  文案生成        → 模板拼装推荐理由与避雷提示
输出：推荐组合 + 理由 + 避雷清单
```

## 2. Layer 0 · 目标计算

### 2.1 BMR（Mifflin-St Jeor 公式）

```python
def calc_bmr(gender: int, weight_kg: float, height_cm: float, age: int) -> float:
    base = 10 * weight_kg + 6.25 * height_cm - 5 * age
    return base + 5 if gender == 1 else base - 161
```

### 2.2 TDEE

```python
ACTIVITY_FACTOR = {1: 1.2, 2: 1.375, 3: 1.55, 4: 1.725, 5: 1.9}

def calc_tdee(bmr: float, activity_level: int) -> float:
    return bmr * ACTIVITY_FACTOR[activity_level]
```

### 2.3 目标热量（含安全下限，这是合规红线）

```python
# 1 kg 脂肪约等于 7700 kcal
KCAL_PER_KG_FAT = 7700
SAFETY_FLOOR = {1: 1500, 2: 1200}   # 男 / 女 的每日最低摄入
MAX_DEFICIT_RATIO = 0.25            # 赤字不超过 TDEE 的 25%

def calc_target_kcal(tdee, bmr, gender, goal, goal_rate_kg_wk) -> tuple[float, list[str]]:
    warnings = []
    if goal != 1:                                  # 非减脂
        return (tdee, warnings) if goal == 2 else (tdee * 1.1, warnings)

    deficit = goal_rate_kg_wk * KCAL_PER_KG_FAT / 7

    # 约束一：赤字不超过 TDEE 的 25%
    if deficit > tdee * MAX_DEFICIT_RATIO:
        deficit = tdee * MAX_DEFICIT_RATIO
        warnings.append("rate_too_aggressive")

    target = tdee - deficit

    # 约束二：不低于 BMR
    if target < bmr:
        target = bmr
        warnings.append("below_bmr")

    # 约束三：不低于绝对安全下限
    floor = SAFETY_FLOOR[gender]
    if target < floor:
        target = floor
        warnings.append("below_floor")

    return target, warnings
```

三重约束必须全部实现。当产生 `warnings` 时，UI 上要告知用户"你设定的速率过快，已为你调整为更安全的方案"，而不是静默修正。

### 2.4 营养目标

```python
def calc_target_nutrients(target_kcal: float, weight_kg: float, goal: int) -> dict:
    # 减脂期高蛋白以保留肌肉
    protein_g = weight_kg * (1.8 if goal == 1 else 1.4)
    # 脂肪占总热量 25%
    fat_g = target_kcal * 0.25 / 9
    # 碳水填补剩余热量
    cho_kcal = target_kcal - protein_g * 4 - fat_g * 9
    cho_g = max(cho_kcal / 4, weight_kg * 1.5)   # 碳水下限，避免过低影响状态

    return {
        "energy_kcal": round(target_kcal, 1),
        "protein_g":   round(protein_g, 1),
        "fat_g":       round(fat_g, 1),
        "cho_g":       round(cho_g, 1),
        "fiber_g":     27.0,        # 成人每日膳食纤维参考量
        "sodium_mg":   2000.0,      # 上限型指标
    }
```

注意 `sodium_mg` 与其他指标性质不同：**它是上限型指标**（越少越好），而蛋白质/纤维是目标型（要达成）。引擎中必须区分这两类，否则会把"钠摄入不足"当成缺口去填补。

营养素类型定义：

| 类型 | 营养素 | 引擎处理方式 |
| --- | --- | --- |
| 目标型（need） | protein_g, fiber_g, cho_g | 缺口越大越需要填补，加分 |
| 上限型（cap） | sodium_mg, sugar_g, fat_g | 接近或超过上限时，含量高的食物降权或排除 |
| 平衡型（budget） | energy_kcal | 有明确额度，超出则排除 |

## 3. Layer 1 · 缺口计算

### 3.1 今日剩余额度

```python
EXERCISE_CREDIT_RATIO = 0.7   # 运动消耗只计入 70%，保守估算

def calc_remaining(target_nutrients, today_intake, today_exercise_kcal):
    credit = today_exercise_kcal * EXERCISE_CREDIT_RATIO
    remaining = {}
    for k, target in target_nutrients.items():
        consumed = today_intake.get(k, 0)
        if k == "energy_kcal":
            remaining[k] = target + credit - consumed
        else:
            remaining[k] = target - consumed
    return remaining
```

运动消耗只按 70% 折算的原因：MET 公式的估算误差较大，且用户普遍高估运动强度。如果全额计入，很容易导致实际赤字消失，用户长期不见效果后会归因于产品无效。

### 3.2 按餐次分配

```python
MEAL_RATIO = {"breakfast": 0.25, "lunch": 0.40, "dinner": 0.30, "snack": 0.05}

def alloc_for_meal(remaining, meal_type, remaining_meals: list[str]):
    """把剩余额度按未来餐次的比例分配给当前餐"""
    total_ratio = sum(MEAL_RATIO[m] for m in remaining_meals)
    share = MEAL_RATIO[meal_type] / total_ratio
    return {k: v * share for k, v in remaining.items()}
```

**为什么要按"剩余餐次"重新归一化**：如果用户午餐吃超了，晚餐的额度应该被压缩，而不是继续按固定 30% 分配。这个动态分配是让全天总量可控的关键。

### 3.3 缺口向量

```python
def calc_gaps(meal_budget, target_nutrients) -> dict:
    """返回归一化缺口，用于打分。>0 表示需要补充"""
    gaps = {}
    for k, v in meal_budget.items():
        if k in CAP_NUTRIENTS:      # 上限型
            gaps[k] = -1.0 if v <= 0 else 0.0
        else:
            denom = target_nutrients.get(k) or 1
            gaps[k] = max(v, 0) / denom
    return gaps
```

## 4. Layer 2 · 硬约束过滤（避雷规则引擎）

### 4.1 规则优先级

```
P0  过敏原            → exclude（绝对，不可覆盖）
P1  忌口 / 饮食类型    → exclude
P2  额度硬约束         → exclude（单品热量 > 本餐额度 × 1.2）
P3  营养冲突          → exclude 或 downweight（如今日脂肪已超标）
P4  目标相关避雷       → downweight + warn（如减脂期油炸食物）
P5  偏好负反馈         → downweight
```

P0 和 P1 是**绝对排除**，任何打分逻辑都不能让它们进入结果集。实现上必须在召回阶段就用 SQL 过滤掉，而不是召回后再筛 —— 避免因代码分支遗漏导致过敏原食物出现在推荐里。

### 4.2 规则条件的 DSL

存于 `avoid_rules.condition`（JSONB），结构：

```json
{
  "all": [
    { "field": "cook_method", "op": "in", "value": ["deepfry"] },
    { "field": "user.goal", "op": "eq", "value": 1 }
  ]
}
```

支持的组合器：`all`（与）、`any`（或）、`not`。支持的字段来源：
- `food.*`：食物的任意字段与标签（`cook_method`、`attr_tags`、`category`、`nutrients.xxx`）
- `user.*`：用户 profile 与偏好
- `today.*`：今日已摄入的营养累计与占目标比例

支持的操作符：`eq`、`ne`、`in`、`nin`、`gt`、`gte`、`lt`、`lte`、`contains`、`overlap`（数组交集）。

### 4.3 MVP 避雷规则集（减脂目标）

这些规则直接对应你要的"告诉用户避雷什么"功能。

| code | 条件 | 动作 | 文案 |
| --- | --- | --- | --- |
| `avoid_deepfry` | `cook_method = deepfry` | downweight 0.2 + warn | 油炸类脂肪密度高，同样分量热量约为清蒸的 2-3 倍，减脂期建议减少 |
| `avoid_sugary_drink` | `category = beverage` 且 `nutrients.sugar_g > 5`（每100g） | downweight 0.1 + warn | 含糖饮料提供热量但几乎不提供饱腹感，容易在不察觉中超出额度 |
| `avoid_high_sodium` | `nutrients.sodium_mg > 800`（每100g） | warn | 高钠饮食容易导致水分滞留，会让体重读数波动，影响你判断进展 |
| `avoid_alcohol` | `category = alcohol` | downweight 0.1 + warn | 酒精本身提供热量且会抑制脂肪氧化 |
| `avoid_refined_snack` | `attr_tags ⊇ [processed]` 且 `nutrients.sugar_g > 15` | downweight 0.2 + warn | 精制糖零食升糖快、饱腹感低 |
| `cap_fat_exceeded` | `today.fat_g / target.fat_g > 0.9` 且 `food.nutrients.fat_g > 15` | exclude | 今日脂肪已接近目标，先避开高脂食物 |
| `cap_sodium_exceeded` | `today.sodium_mg / 2000 > 0.9` | downweight 0.3 | 今日钠摄入已较高 |
| `budget_overflow` | `food_kcal_at_default_portion > meal_budget × 1.2` | exclude | （不展示，静默过滤） |
| `low_protein_day` | `today.protein_g / target.protein_g < 0.5` 且当前是晚餐 | boost 高蛋白食物 | 今天蛋白质还差较多，优先补充 |

**重要的设计取舍**：油炸类用 `downweight` 而非 `exclude`。原因是完全屏蔽会让用户觉得产品不切实际（外卖党很难完全避开），降权则表现为"尽量不推荐，但如果你就是要吃，我告诉你怎么控制总量"。这个尺度对留存很关键 —— 过于严苛的减脂工具会被放弃。

### 4.4 避雷清单的独立输出

除了在推荐中过滤，还要独立输出一份"今日避雷清单"（用户明确要的功能）。它由**当日已触发或即将触发的 cap 类规则**生成：

```python
def build_avoid_list(user, today_intake, targets) -> list[dict]:
    items = []
    # 基于目标的固定避雷项
    for rule in load_rules(goal=user.goal, action_in=["warn", "downweight"]):
        if rule.is_goal_level:      # 与今日摄入无关的通用建议
            items.append({"title": rule.short_title, "reason": rule.message,
                          "level": "info"})
    # 基于今日实际摄入的动态避雷项
    for nutrient in CAP_NUTRIENTS:
        ratio = today_intake.get(nutrient, 0) / targets[nutrient]
        if ratio > 0.9:
            items.append({"title": CAP_TITLE[nutrient],
                          "reason": f"今日已达目标的 {ratio:.0%}",
                          "level": "alert"})
    return items
```

动态项（基于今日实际摄入）比固定项有价值得多，因为它是**个性化且当日有效**的。UI 上应把动态项置顶。

## 5. Layer 3 · 候选召回

### 5.1 召回策略

按角色分别召回，每个角色取 20-50 条候选：

```python
ROLE_PLAN = {
    "breakfast": ["staple", "protein", "dairy_or_fruit"],
    "lunch":     ["staple", "protein", "vegetable"],
    "dinner":    ["staple", "protein", "vegetable"],
    "snack":     ["snack_healthy"],
}

def recall(user, prefs, scene, meal_type, role) -> list[Food]:
    return query(f"""
        SELECT * FROM foods
        WHERE review_status = 1
          AND %(scene)s = ANY(scene_tags)
          AND %(role)s   = ANY(role_tags)
          AND (%(meal)s  = ANY(meal_tags) OR meal_tags = '{{}}')
          -- P0/P1 硬排除下沉到 SQL
          AND NOT (ingredient_tags && %(allergens)s)
          AND NOT (ingredient_tags && %(avoid_ingredients)s)
          AND NOT (category = ANY(%(avoid_categories)s))
        ORDER BY popularity DESC
        LIMIT 50
    """)
```

### 5.2 场景标签的重要性

`scene_tags` 决定推荐是否**可执行**。这是本产品最容易失败的地方：推荐一道需要烤箱的菜给外卖党，或推荐食堂没有的菜，用户会立刻失去信任。

食物库建设时的标注要求：
- `takeout`：外卖平台常见、能搜到的菜品名
- `canteen`：食堂常见的家常菜与主食
- `homecook`：食材易得、做法在 3 步以内

一个食物可以有多个场景标签。**宁可标少，不要标错** —— 标少只是候选池小，标错会直接导致推荐不可用。

## 6. Layer 4 · 单品打分

```python
WEIGHTS = {
    "nutrition_fit": 0.35,   # 营养缺口匹配度
    "kcal_fit":      0.20,   # 热量适配度
    "affinity":      0.20,   # 用户偏好
    "repeat_penalty":-0.15,  # 近期重复惩罚
    "rule_penalty":  -0.10,  # 避雷软惩罚
}

def score_food(food, gaps, meal_budget, affinity, last_eaten_days, rule_factor):
    # 1. 营养匹配度：食物在默认份量下能填补多少缺口（只算目标型营养素）
    portion = default_portion_grams(food)
    n = scale_nutrients(food.nutrients, portion)
    fit = 0.0
    for k in NEED_NUTRIENTS:                 # protein_g, fiber_g, cho_g
        if gaps.get(k, 0) > 0:
            contribution = min(n.get(k, 0) / max(meal_budget[k], 1e-6), 1.0)
            fit += contribution * gaps[k]
    fit = fit / max(sum(v for k, v in gaps.items() if k in NEED_NUTRIENTS), 1e-6)

    # 2. 热量适配度：越接近本餐额度中该角色应占的份额越好
    expect = meal_budget["energy_kcal"] * ROLE_KCAL_SHARE[food.primary_role]
    kcal_fit = 1 - min(abs(n["energy_kcal"] - expect) / max(expect, 1), 1.0)

    # 3. 偏好度：-1 ~ 1
    aff = affinity            # 来自 user_food_affinity.affinity

    # 4. 近期重复惩罚：3 天内吃过则递减
    repeat = max(0, 1 - last_eaten_days / 3) if last_eaten_days is not None else 0

    return (WEIGHTS["nutrition_fit"] * fit
            + WEIGHTS["kcal_fit"] * kcal_fit
            + WEIGHTS["affinity"] * aff
            + WEIGHTS["repeat_penalty"] * repeat
            + WEIGHTS["rule_penalty"] * (1 - rule_factor))
```

权重值是**初始猜测，必须靠数据调优**。调优依据是 `recommendation_feedback` 中的采纳率与换一换率。建议每个权重都做成配置项，不要写死在代码里。

## 7. Layer 5 · 组合生成

单品推荐价值有限，用户需要的是"一餐吃什么"。采用**按角色贪心 + 全局校验**：

```python
def build_meal(candidates_by_role, meal_budget, role_plan):
    selected = []
    remaining = dict(meal_budget)

    # 关键：先选蛋白源。减脂期蛋白质是最难达成的目标，
    # 若最后再选，额度往往已被主食占满。
    for role in order_roles_protein_first(role_plan):
        pool = candidates_by_role[role]
        best = pick_best(pool, remaining, exclude=selected)
        if best is None:
            continue
        selected.append(best)
        remaining = subtract(remaining, best.nutrients_at_portion)

    # 全局校验：总热量必须落在额度的 85%~105% 区间
    total = sum_kcal(selected)
    if not (meal_budget["energy_kcal"] * 0.85 <= total
            <= meal_budget["energy_kcal"] * 1.05):
        selected = adjust_portions(selected, meal_budget)   # 见 Layer 6

    return selected
```

**"蛋白优先"是这个算法里最重要的一条**。减脂饮食的核心矛盾是"热量要低、蛋白要高"，如果按主食→蛋白→蔬菜的自然顺序选，主食会先吃掉大部分热量额度，导致蛋白质永远达不到目标。

### 7.1 多样性约束

- 同一餐内不出现同 `category` 的两个食物（除蔬菜类）
- 同一天内不重复出现同一 `food_id`
- 近 3 天内出现过的食物在打分阶段已被降权

## 8. Layer 6 · 份量微调

推荐的份量必须落在"用户能理解且能执行"的粒度上，不能输出"鸡胸肉 137g"这样的数字。

```python
def adjust_portions(items, budget):
    """按可选份量档位调整，而非连续调整克数"""
    ratio = budget["energy_kcal"] / sum_kcal(items)
    for item in items:
        # 只在该食物已配置的 portion 档位中选最接近的
        target_g = item.grams * ratio
        item.portion = nearest_portion(item.food_id, target_g)
        item.grams = item.portion.grams
    return items
```

这就是为什么 `food_portions` 表必须为每个食物配置多个档位（见 03 文档）。输出"一碗米饭（约 150g）"而不是"米饭 137g"。

## 9. Layer 7 · 换一换

用户明确要求的功能。核心设计是**在营养生态位内替换**。

```python
def swap(rec_id, food_id_to_replace, reason: str):
    rec = load_recommendation(rec_id)
    target = find_item(rec, food_id_to_replace)

    # 1. 记录反馈（区分原因很重要）
    save_feedback(rec.user_id, rec_id, food_id_to_replace, "swap", reason)
    if reason == "dont_like":
        decay_affinity(rec.user_id, food_id_to_replace, delta=-0.3)
    # reason == "not_available" 不影响口味偏好，
    # 而是记为场景标签问题，累积到一定次数后触发标签复核

    # 2. 在同角色、同营养生态位内找替代
    niche = {
        "role": target.role,
        "kcal_range":    (target.kcal * 0.8,    target.kcal * 1.2),
        "protein_range": (target.protein * 0.8, target.protein * 1.3),
    }
    alternatives = recall_by_niche(niche, exclude=rec.all_food_ids())
    alternatives = apply_hard_filters(alternatives, rec.user_id)
    ranked = [score_food(f, ...) for f in alternatives]

    # 3. 替换后重新校验全餐总额度
    new_rec = replace_item(rec, target, ranked[0])
    return validate_and_adjust(new_rec)
```

**区分换一换原因是这个设计里最有价值的细节**：
- `not_available`（买不到 / 食堂没有）→ 说明 `scene_tags` 标注有误，应累积统计并触发数据修正，**不应**降低用户对该食物的偏好分
- `dont_like`（不爱吃）→ 真实口味负反馈，降低 affinity
- `too_much`（分量太大）→ 调整份量档位，不换食物

如果把这三种混为一谈，模型会学出错误的偏好（比如把"外卖平台没有西兰花"学成"用户讨厌西兰花"）。

### 9.1 换一换的次数限制

免费用户每餐限 3 次，这是天然的付费钩子（见 01 文档付费点设计）。限制计数必须在**云端**，不能放本地。

## 10. 冷启动方案

这是本定位的最大风险点：推荐依赖历史，但历史来自使用。解决思路是**分级降级，零数据也可用**。

| 阶段 | 可用数据 | 推荐策略 | 质量 |
| --- | --- | --- | --- |
| **L0 · 首次打开** | 仅 6 项基础信息 | 纯营养平衡驱动：按目标热量与营养目标，从场景内高热度食物中组合 | 可用，泛化 |
| **L1 · 完成偏好问卷** | + 忌口/过敏/辣度/场景 | 加入硬过滤，排除不吃的东西 | **明显可用，这是关键跃升** |
| **L2 · 记录 ≥ 3 天** | + 食物偏好频次 | 加入 affinity 打分与重复惩罚 | 开始个性化 |
| **L3 · 记录 ≥ 7 天** | + 营养达成趋势 | 加入趋势修正（如长期蛋白不足则持续加权高蛋白） | 良好 |
| **L4 · 记录 ≥ 21 天 + 体重数据** | + 实际体重变化 | 目标校准：若实际减重速率显著偏离预期，调整 TDEE 估算值 | 优秀 |

**L1 是最重要的投资**：一份 30 秒的偏好问卷能把首日推荐从"泛泛而谈"提升到"看起来懂我"，而它的开发成本只有几个表单页。这是投入产出比最高的一环，必须放进 MVP。

### 10.1 L4 的 TDEE 自校准（P1，但价值很高）

公式估算的 TDEE 存在个体误差。有了体重数据后可以反推真实值：

```python
def calibrate_tdee(user_id, days=21):
    """用实际体重变化反推真实 TDEE"""
    logs = load_weight_logs(user_id, days)
    intake = load_avg_daily_intake(user_id, days)
    if len(logs) < 10 or intake is None:
        return None

    # 用首末各 3 天的均值，抵消日常波动
    delta_kg = avg(logs[-3:]) - avg(logs[:3])
    actual_deficit_per_day = -delta_kg * KCAL_PER_KG_FAT / days
    estimated_tdee = intake + actual_deficit_per_day

    # 与公式值差异超过 20% 时不采纳，通常意味着记录不完整
    formula_tdee = load_profile(user_id).tdee_kcal
    if abs(estimated_tdee - formula_tdee) / formula_tdee > 0.2:
        return None
    return estimated_tdee
```

这个功能是**真正的差异化能力**，而且是竞品普遍做得不好的地方——它把"记录"变成了"让推荐越来越准"的投资，形成正反馈闭环，直接对抗记录类产品的流失问题。注意必须设置偏差阈值，因为记录不完整（漏记）会导致反推出严重偏低的 TDEE。

## 12. 算法版本与调优

- `recommendations.version` 记录算法版本，便于回溯和对比不同版本的采纳率。
- 所有权重、比例、阈值集中在一个配置模块，支持不发版调整。
- 核心调优指标：**推荐采纳率**（目标 ≥ 40%）与**换一换次数/推荐次数**（目标 ≤ 1.5）。
- 每次调整权重后，对比调整前后 7 天的这两个指标，避免凭感觉调参。

## 13. 单元测试要求（这部分不能省）

营养计算与安全边界是**必须有测试覆盖**的部分，因为出错会直接产生健康风险且用户无法察觉：

1. BMR/TDEE 计算：用已知输入验证输出（男女各若干组）。
2. 安全下限：构造极端输入（如身高 150cm 女性设定每周减 2kg），断言输出不低于 1200 kcal 且返回 warning。
3. 过敏原过滤：断言含过敏原食物在任何权重配置下都不出现在结果中。
4. 额度校验：断言生成的组合总热量落在额度的 85%~105% 区间。
5. 上限型营养素：断言钠摄入不会被当作缺口去填补。
6. 换一换：断言替换后总热量仍在额度内，且不引入过敏原。
