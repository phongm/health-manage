# 03 · 数据模型

数据库：PostgreSQL（独立 database）。以下 DDL 为设计稿，实际落地通过 Alembic 迁移管理。

## 1. 营养素数据规范

所有营养素统一用 `JSONB` 存储，字段名与单位**全局固定**，避免各处不一致。基准统一为**每 100 克可食部**。

```json
{
  "energy_kcal": 167.0,
  "protein_g": 19.4,
  "fat_g": 5.0,
  "cho_g": 2.5,
  "fiber_g": 0.0,
  "sodium_mg": 63.0,
  "sugar_g": 0.5,
  "calcium_mg": 9.0,
  "iron_mg": 1.4,
  "vitamin_a_ug": 16.0,
  "vitamin_c_mg": 0.0
}
```

规则：
- MVP 只强制要求前 6 项（`energy_kcal`、`protein_g`、`fat_g`、`cho_g`、`fiber_g`、`sodium_mg`），其余可缺失。
- 缺失字段用**不存在**表示，不用 0 —— 0 表示"确认含量为零"，缺失表示"数据未知"。这个区分在做营养统计时很重要，否则会把未知当成零导致低估。
- 单位后缀写进字段名（`_g` / `_mg` / `_ug` / `_kcal`），避免单位歧义。
- 扩展新营养素只需新增字段，不改表结构。

## 2. 用户相关表

### 2.1 users

```sql
CREATE TABLE users (
    id           BIGSERIAL PRIMARY KEY,
    openid       VARCHAR(64)  NOT NULL UNIQUE,
    unionid      VARCHAR(64),
    status       SMALLINT     NOT NULL DEFAULT 1,  -- 1 正常 / 0 禁用 / -1 已注销
    created_at   TIMESTAMPTZ  NOT NULL DEFAULT now(),
    updated_at   TIMESTAMPTZ  NOT NULL DEFAULT now()
);
CREATE INDEX idx_users_unionid ON users(unionid) WHERE unionid IS NOT NULL;
```

### 2.2 user_profiles

```sql
CREATE TABLE user_profiles (
    user_id          BIGINT PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE,
    gender           SMALLINT     NOT NULL,          -- 1 男 / 2 女
    birth_year       SMALLINT     NOT NULL,          -- 存出生年份而非年龄，避免逐年失效
    height_cm        NUMERIC(5,1) NOT NULL,
    weight_kg        NUMERIC(5,1) NOT NULL,          -- 当前体重，随体重记录同步更新
    body_fat_pct     NUMERIC(4,1),                   -- 可选
    activity_level   SMALLINT     NOT NULL,          -- 1~5，见下表
    goal             SMALLINT     NOT NULL,          -- 1 减脂 / 2 维持 / 3 增肌
    goal_rate_kg_wk  NUMERIC(3,2)  DEFAULT 0.5,      -- 目标周减重速率
    target_weight_kg NUMERIC(5,1),
    -- 缓存的计算结果，profile 变更时重算，避免每次请求重复计算
    bmr_kcal         NUMERIC(7,1),
    tdee_kcal        NUMERIC(7,1),
    target_kcal      NUMERIC(7,1),
    target_nutrients JSONB,                          -- 营养目标向量
    is_excluded      BOOLEAN      NOT NULL DEFAULT false,  -- 命中排除人群
    exclude_reason   VARCHAR(64),
    created_at       TIMESTAMPTZ  NOT NULL DEFAULT now(),
    updated_at       TIMESTAMPTZ  NOT NULL DEFAULT now()
);
```

`activity_level` 取值与系数（用于 TDEE 计算）：

| 值 | 含义 | 系数 |
| --- | --- | --- |
| 1 | 久坐，几乎不运动 | 1.2 |
| 2 | 轻度活动，每周 1-3 次 | 1.375 |
| 3 | 中度活动，每周 3-5 次 | 1.55 |
| 4 | 高强度，每周 6-7 次 | 1.725 |
| 5 | 极高强度 / 体力工作 | 1.9 |

`is_excluded` 字段用于标记命中排除人群（慢病、孕期、未成年、BMI 过低等）的用户。命中后仅提供记录功能，不返回推荐 —— 这是合规要求，必须在数据层留痕。

### 2.3 user_preferences

冷启动推荐质量的关键输入。

```sql
CREATE TABLE user_preferences (
    user_id          BIGINT PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE,
    allergens        TEXT[]  DEFAULT '{}',   -- 过敏原标签，硬性排除
    avoid_ingredients TEXT[] DEFAULT '{}',   -- 忌口食材，硬性排除
    avoid_categories TEXT[]  DEFAULT '{}',   -- 不吃的类别，如 'organ_meat'（内脏）
    diet_type        VARCHAR(32),            -- 'omnivore' / 'vegetarian' / 'vegan' / 'pescatarian'
    spice_level      SMALLINT DEFAULT 2,     -- 0 不吃辣 ~ 3 嗜辣
    scene_default    VARCHAR(16) DEFAULT 'takeout',  -- takeout / canteen / homecook
    scene_by_meal    JSONB,                  -- 按餐次覆盖：{"lunch":"canteen","dinner":"homecook"}
    updated_at       TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

`allergens` 与 `avoid_ingredients` 是**硬性排除**，在推荐引擎中优先级最高，任何情况下不得被打分逻辑覆盖。

## 3. 食物库

### 3.1 foods

```sql
CREATE TABLE foods (
    id             BIGSERIAL PRIMARY KEY,
    name           VARCHAR(128) NOT NULL,
    aliases        TEXT[]  DEFAULT '{}',       -- 别名，用于搜索命中
    category       VARCHAR(32)  NOT NULL,      -- 见 3.3 分类
    -- 推荐引擎依赖的标签
    scene_tags     TEXT[]  DEFAULT '{}',       -- takeout / canteen / homecook
    meal_tags      TEXT[]  DEFAULT '{}',       -- breakfast / lunch / dinner / snack
    cook_method    VARCHAR(16),                -- steam/boil/stirfry/deepfry/grill/raw/stew
    role_tags      TEXT[]  DEFAULT '{}',       -- staple(主食)/protein/vegetable/fruit/soup/dairy
    attr_tags      TEXT[]  DEFAULT '{}',       -- high_protein/high_fiber/high_sodium/high_sugar/processed 等
    ingredient_tags TEXT[] DEFAULT '{}',       -- 含有的食材，用于忌口与过敏匹配
    -- 营养数据（每 100g 可食部）
    nutrients      JSONB   NOT NULL,
    edible_pct     NUMERIC(4,1) DEFAULT 100.0, -- 可食部比例
    -- 数据溯源与质量
    source         VARCHAR(32)  NOT NULL,      -- self_built / usda / label / ugc / licensed
    source_ref     VARCHAR(256),
    confidence     SMALLINT     DEFAULT 3,     -- 1~5，影响推荐时是否优先采用
    review_status  SMALLINT     NOT NULL DEFAULT 1,  -- 0 待审 / 1 已用 / -1 拒绝
    barcode        VARCHAR(32),                -- 预包装食品条码
    popularity     INTEGER      NOT NULL DEFAULT 0,  -- 全局被记录次数，用于搜索排序与召回
    created_at     TIMESTAMPTZ  NOT NULL DEFAULT now(),
    updated_at     TIMESTAMPTZ  NOT NULL DEFAULT now()
);

CREATE INDEX idx_foods_category    ON foods(category);
CREATE INDEX idx_foods_scene_tags  ON foods USING GIN(scene_tags);
CREATE INDEX idx_foods_role_tags   ON foods USING GIN(role_tags);
CREATE INDEX idx_foods_attr_tags   ON foods USING GIN(attr_tags);
CREATE INDEX idx_foods_ingredient  ON foods USING GIN(ingredient_tags);
CREATE INDEX idx_foods_aliases     ON foods USING GIN(aliases);
CREATE INDEX idx_foods_barcode     ON foods(barcode) WHERE barcode IS NOT NULL;
CREATE INDEX idx_foods_nutrients   ON foods USING GIN(nutrients);
```

**`role_tags` 是推荐引擎的核心字段**：组合推荐（主食 + 蛋白 + 蔬菜）完全依赖它，录入食物数据时必须准确标注，不能留空。

`source` 字段用于版权风险管理：只允许 `self_built`（自行整理）、`usda`（美国公开数据）、`label`（依 GB 28050 标注的包装营养成分表）、`ugc`（用户共建）、`licensed`（已购授权）。**禁止录入来源为未授权出版物的数据。**

### 3.2 food_portions

用户不会输入克数，必须提供常见份量选项。这张表直接决定录入体验。

```sql
CREATE TABLE food_portions (
    id         BIGSERIAL PRIMARY KEY,
    food_id    BIGINT NOT NULL REFERENCES foods(id) ON DELETE CASCADE,
    label      VARCHAR(32)  NOT NULL,      -- '一碗' / '中份' / '一个' / '一勺'
    grams      NUMERIC(7,1) NOT NULL,
    is_default BOOLEAN      NOT NULL DEFAULT false,
    sort_order SMALLINT     DEFAULT 0
);
CREATE INDEX idx_portions_food ON food_portions(food_id);
```

每个食物至少配置 2-3 个份量选项，且必须有一个 `is_default`。

### 3.3 食物分类（category 取值）

参照通用食物分类习惯，用于筛选与统计：`grain`（谷类及制品）、`tuber`（薯类淀粉）、`legume`（干豆及制品）、`vegetable`、`mushroom_algae`（菌藻）、`fruit`、`nut_seed`、`livestock_meat`、`poultry`、`dairy`、`egg`、`aquatic`（鱼虾蟹贝）、`snack_dessert`、`fast_food`（速食）、`beverage`、`alcohol`、`sugar`、`oil_fat`、`condiment`、`dish`（复合菜品）、`packaged`（预包装食品）。

### 3.4 food_contributions（UGC，P1）

```sql
CREATE TABLE food_contributions (
    id           BIGSERIAL PRIMARY KEY,
    user_id      BIGINT NOT NULL REFERENCES users(id),
    barcode      VARCHAR(32),
    name         VARCHAR(128),
    image_url    VARCHAR(512),     -- 营养成分表照片
    parsed       JSONB,            -- OCR/AI 解析结果
    status       SMALLINT NOT NULL DEFAULT 0,  -- 0 待审 / 1 已采纳 / -1 拒绝
    merged_food_id BIGINT REFERENCES foods(id),
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

UGC 数据**必须经审核**才能进入 `foods` 表，未审核数据不参与推荐。审核可先人工，量大后引入规则自动校验（如三大营养素折算热量与标注热量的偏差是否在合理范围内）。

### 3.5 food_recipes（配方分解）

复合菜品（如"清蒸鸡胸"）的营养数据不手工录入，而是由基础食材按重量配比自动计算。这是食物库建设的核心效率手段，详见 [06 文档第 5.1 节](./06-实施路线图.md#51-配方分解法)。

```sql
CREATE TABLE food_recipes (
    id            BIGSERIAL PRIMARY KEY,
    dish_food_id  BIGINT NOT NULL REFERENCES foods(id) ON DELETE CASCADE,
    ingredient_id BIGINT NOT NULL REFERENCES foods(id),
    grams         NUMERIC(7,1) NOT NULL,
    note          VARCHAR(64)
);
CREATE INDEX idx_recipes_dish ON food_recipes(dish_food_id);
```

设计要点：

- `foods.nutrients` 对复合菜品是**物化存储**（由脚本按配方计算后写入），不在查询时实时计算 —— 推荐引擎的召回与打分会高频读取营养数据，实时计算会带来不必要的开销。
- 配方或基础食材数据变更后，需重跑计算脚本刷新受影响菜品的 `nutrients`。
- 配方同时服务产品功能：场景 C（自己做饭）的推荐可直接把配方作为食材清单展示给用户。
- 基础食材自身不需要配方记录，`source` 为 `usda` 或 `label`。

## 4. 记录表

### 4.1 intake_logs

```sql
CREATE TABLE intake_logs (
    id            BIGSERIAL PRIMARY KEY,
    user_id       BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    log_date      DATE   NOT NULL,               -- 冗余存储，便于按日聚合
    meal_type     VARCHAR(16) NOT NULL,          -- breakfast/lunch/dinner/snack
    food_id       BIGINT REFERENCES foods(id),
    food_name     VARCHAR(128) NOT NULL,         -- 冗余，兼容库外食物
    grams         NUMERIC(7,1) NOT NULL,
    portion_label VARCHAR(32),
    -- 营养快照：记录时的营养值，不随食物库更新而变
    nutrients_snapshot JSONB NOT NULL,
    input_source  VARCHAR(16) NOT NULL,          -- text/voice/image/recommend
    from_rec_id   BIGINT,                        -- 若来自采纳推荐，记录来源推荐 ID
    logged_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_intake_user_date ON intake_logs(user_id, log_date);
CREATE INDEX idx_intake_user_food ON intake_logs(user_id, food_id);
```

**营养快照设计很重要**：必须把记录时点的营养值冻结存下来，不能只存 `food_id` 后续实时计算。原因是食物库数据会被修正（尤其 UGC 来源），若实时计算，用户的历史统计会在你修数据时莫名变化，这会摧毁数据可信度。

`from_rec_id` 用于统计推荐采纳率，是衡量推荐质量的核心指标来源。

### 4.2 exercise_logs 与 exercises

```sql
CREATE TABLE exercises (
    id       BIGSERIAL PRIMARY KEY,
    name     VARCHAR(64) NOT NULL,
    aliases  TEXT[] DEFAULT '{}',
    category VARCHAR(32),                 -- cardio / strength / daily
    met_low  NUMERIC(4,2) NOT NULL,       -- 低强度 MET
    met_mid  NUMERIC(4,2) NOT NULL,
    met_high NUMERIC(4,2) NOT NULL
);

CREATE TABLE exercise_logs (
    id           BIGSERIAL PRIMARY KEY,
    user_id      BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    log_date     DATE NOT NULL,
    exercise_id  BIGINT REFERENCES exercises(id),
    exercise_name VARCHAR(64) NOT NULL,
    duration_min SMALLINT NOT NULL,
    intensity    SMALLINT NOT NULL DEFAULT 2,   -- 1 低 / 2 中 / 3 高
    kcal_burned  NUMERIC(7,1) NOT NULL,
    logged_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_exercise_user_date ON exercise_logs(user_id, log_date);
```

消耗计算公式：`kcal = MET × 体重kg × 时长h`。按 `intensity` 选用对应的 MET 值。

⚠️ 产品上要注意：运动消耗的估算误差较大，且用户容易用"我运动了所以可以多吃"来抵消赤字。建议在 UI 上**只把运动消耗的一部分（如 70%）计入可增加的摄入额度**，并明确说明这是保守估算。

### 4.3 weight_logs

```sql
CREATE TABLE weight_logs (
    id           BIGSERIAL PRIMARY KEY,
    user_id      BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    log_date     DATE NOT NULL,
    weight_kg    NUMERIC(5,1) NOT NULL,
    body_fat_pct NUMERIC(4,1),
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (user_id, log_date)
);
```

展示时用**7 日移动平均**而非单日值 —— 单日体重受水分影响波动大，直接展示会让用户在正常波动时产生挫败感。

## 5. 推荐相关表

### 5.1 recommendations

```sql
CREATE TABLE recommendations (
    id          BIGSERIAL PRIMARY KEY,
    user_id     BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    rec_date    DATE NOT NULL,
    meal_type   VARCHAR(16) NOT NULL,
    scene       VARCHAR(16) NOT NULL,
    -- 推荐内容：食物组合
    items       JSONB NOT NULL,   -- [{food_id, name, grams, portion_label, role}]
    -- 生成依据，用于可解释性与问题排查
    context     JSONB NOT NULL,   -- {remaining_kcal, gaps:{...}, triggered_rules:[...], scores:{...}}
    version     VARCHAR(16) NOT NULL,   -- 推荐算法版本，用于 A/B 与回溯
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_rec_user_date ON recommendations(user_id, rec_date);
```

`context` 字段必须完整记录生成依据。这不是可选的日志 —— 当用户质疑"为什么推荐这个"时，你需要能复现当时的判断；调优算法时也需要这些数据。

### 5.2 recommendation_feedback

偏好学习的数据来源。

```sql
CREATE TABLE recommendation_feedback (
    id       BIGSERIAL PRIMARY KEY,
    user_id  BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    rec_id   BIGINT NOT NULL REFERENCES recommendations(id) ON DELETE CASCADE,
    food_id  BIGINT REFERENCES foods(id),
    action   VARCHAR(16) NOT NULL,   -- accept / swap / ignore / dislike
    reason   VARCHAR(32),            -- 换一换原因：not_available/dont_like/too_much/other
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_feedback_user_food ON recommendation_feedback(user_id, food_id);
```

**收集换一换的原因很有价值**：`not_available`（买不到）说明场景标签错了，`dont_like`（不爱吃）才是口味偏好信号。两者不能混为一谈，否则会把"外卖平台没有"误学成"用户讨厌"。

### 5.3 user_food_affinity（偏好模型，物化视图或定时任务表）

```sql
CREATE TABLE user_food_affinity (
    user_id     BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    food_id     BIGINT NOT NULL REFERENCES foods(id) ON DELETE CASCADE,
    eat_count   INTEGER NOT NULL DEFAULT 0,
    accept_count INTEGER NOT NULL DEFAULT 0,
    dislike_count INTEGER NOT NULL DEFAULT 0,
    last_eaten_at DATE,
    affinity    NUMERIC(5,3) NOT NULL DEFAULT 0,  -- 综合亲和度 -1 ~ 1
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (user_id, food_id)
);
```

由定时任务（或写入时增量更新）维护。`last_eaten_at` 用于近期重复度惩罚。

## 6. 规则与参考数据表

### 6.1 avoid_rules（避雷规则）

规则入库而非硬编码，便于不发版热更新。

CREATE TABLE nutrient_references (

## 7. 小程序本地缓存结构

对应 02 文档第 4.2 节，具体 key 设计：

```ts
// core/storage/keys.ts
const KEYS = {
  profile:   'profile',              // { ...user_profile, syncedAt }
  prefs:     'prefs',
  weight:    'weight',               // 最近 90 天
  foodsHot:  'foods_hot',            // 高频食物，限 500 条
  records:   (ym: string) => `rec_${ym}`,   // rec_2026_08，只保留最近 3 个月
  recIndex:  'rec_index',            // 已缓存的月份列表
  syncQueue: 'sync_queue',           // 待同步操作
  meta:      'meta',                 // { lastSyncAt, schemaVersion }
} as const;
```

写入约束（必须在 storage 抽象层强制检查）：

1. 单个 key 序列化后不得超过 **900KB**（留出安全余量，上限为 1MB）。超出时按月分片或淘汰最旧数据。
2. 总占用不得超过 **8MB**（上限 10MB）。超出时按「最旧月份记录 → 食物库缓存」的顺序淘汰。
3. 每次写入前检查 `schemaVersion`，版本不匹配时执行迁移或清空重拉（清空前必须确认云端已有数据）。
4. 所有本地写入是**缓存操作**，不是持久化操作。任何本地数据丢失都必须能从云端完整恢复。

## 8. 数据保留与合规

- 用户注销：`users.status = -1`，并在约定期限内物理删除其 `intake_logs`、`weight_logs`、`exercise_logs`、`recommendations` 等个人数据。
- 提供数据导出接口（P2），输出用户全部记录的 JSON/CSV。
- 数据库定期备份，备份文件加密存储。
- 健康数据属于个人敏感信息，日志中禁止打印具体的体重、饮食内容等明细。
