## 2. 端云职责划分

这是本架构最重要的设计。划分原则：**用户能立刻看到反馈的计算放端上，需要全量数据或历史数据的计算放云端。**

| 能力 | 位置 | 理由 |
| --- | --- | --- |
| BMR / TDEE / 每日目标计算 | **端上** | 纯函数、输入只有用户 profile，即时响应且离线可用 |
| 今日营养累加、剩余额度 | **端上** | 每次记录后需立刻刷新看板，不能等网络往返 |
| 避雷的即时提示（记录时警示） | **端上** | 用户录入油炸食物时要立刻提示，必须零延迟 |
| 食物搜索 | **端云结合** | 高频食物本地缓存优先命中，未命中走云端 |
| 推荐引擎（召回/打分/组合） | **云端** | 需要全量食物库 + 用户历史 + 偏好模型 |
| 避雷清单生成 | **云端** | 需要结合历史摄入趋势 |
| 图片/语音/文字解析 | **云端** | AI Key 绝不能出现在端上 |
| 数据持久化（真相源） | **云端** | 见第 4 节 |

端上的 `core/` 目录必须是**不依赖任何 `wx.*` API 的纯 TypeScript**。所有小程序 API 调用通过依赖注入传入。这样 Phase 2 迁移到其他端时，这部分代码可直接复用。

## 3. 技术选型与理由

### 3.1 小程序端：原生小程序 + TypeScript

选择理由：单端开发最快，无框架抽象层的调试成本，对单人兼职最友好。

放弃 Taro / uni-app 的理由：跨端能力在 Phase 1 用不上，但构建复杂度和框架层 bug 的排查成本立刻就要付。通过抽出纯 TS 核心包，已经能获得跨端时的大部分收益。

### 3.2 后端：Python + FastAPI

选择 FastAPI 而非 Django/Flask 的理由：

1. **原生异步**。推荐引擎会并发调用 AI 服务与多次数据库查询，异步模型下单机吞吐显著更好。
2. **Pydantic 数据校验**。营养数据有大量数值字段与单位约束，Pydantic 能在接口层直接拦截脏数据，这对营养计算的正确性很关键。
3. **自动生成 OpenAPI 文档**。单人开发时，前后端联调靠自动文档能省下大量沟通与出错成本。
4. **轻量**。独立部署，不与现有业务耦合，出问题时影响面可控。

如果现有服务器上是 Django：建议仍然独立部署 FastAPI 服务，通过 Nginx 按路径分流。理由是本项目与现有业务的生命周期、发布节奏、依赖版本都不同，耦合在一起会互相拖累。仅在服务器资源非常紧张时才考虑合并。

### 3.3 数据库：PostgreSQL

复用现有实例，但**建立独立的 database**（而非仅独立 schema），便于将来独立迁移与备份。

关键用法：营养素数据用 `JSONB` 存储而非为每种营养素建列。理由是营养素种类会持续扩展（MVP 只算 5 项，后续要加微量元素和维生素），用 JSONB 可以在不改表结构的情况下扩展，同时 PostgreSQL 对 JSONB 有完整的索引与查询支持。

### 3.4 Redis（可选，非 MVP 必需）

MVP 阶段可不引入。用户量上来后用于三件事：热门食物库缓存、AI 解析结果缓存（相同输入不重复调用）、按用户的接口限流与 AI 次数配额计数。

## 4. 数据存储策略

**云端 PostgreSQL 为唯一真相源，小程序本地缓存仅作为读加速与离线降级。**

变更原因（重要）：微信官方文档明确「本地缓存的清理时机跟代码包一样，只有在代码包被清理的时候本地缓存才会被清理」——即微信清理代码包时会连带清空用户数据，这不受开发者控制。同时单 key 上限 1MB、总量上限 10MB（开启加密后降为 0.7MB / 7.1MB）。本产品的推荐引擎依赖长期历史数据（口味偏好、食物重复率、体重趋势），数据丢失会直接导致核心功能失效，因此不能把本地作为唯一存储。

### 4.1 写入路径

```
用户操作
  → 立即写本地缓存并刷新 UI（乐观更新）
  → 同时发起云端写入请求
  → 成功：标记已同步
  → 失败：进入待同步队列，下次启动或网络恢复时重试
```

### 4.2 本地缓存内容与分片

本地缓存**只存最近数据**，不做全量镜像：

| Key | 内容 | 上限控制 |
| --- | --- | --- |
| `profile` | 用户基础信息与目标 | 极小 |
| `prefs` | 偏好与忌口 | 极小 |
| `rec_YYYY_MM` | 按月分片的摄入/运动记录 | 只保留最近 3 个月，更早的从云端按需拉取 |
| `foods_hot` | 高频食物库（用户常吃 + 全局热门） | 限制条数，约 300-500 条 |
| `weight` | 最近 90 天体重记录 | 小 |
| `sync_queue` | 待同步操作队列 | 小 |

**按月分片是硬性要求**，不可把所有记录写入单个 key —— 否则用户使用一年后会触发 1MB 单 key 上限导致写入失败。

食物库**不放 storage**，放在代码包（分包）中或首次启动后写入本地缓存的独立 key，避免挤占记录数据的空间。

### 4.3 冲突处理

由于云端为真相源，冲突策略简单：以云端 `updated_at` 为准，本地缓存在启动时按 `since` 增量拉取覆盖。不需要实现 CRDT 或复杂的三方合并。

## 5. AI 能力接入

### 5.1 铁律

**AI 供应商的 API Key 只能存在于服务端环境变量中。** 小程序端永远只调用自己的后端接口，绝不直连 AI 供应商。

### 5.2 各录入方式的实现链路

| 方式 | 链路 | 单次成本（推算） | 阶段 |
| --- | --- | --- | --- |
| 文字 | 端上搜索食物库 → 命中即完成 | **0** | P0 |
| 文字（自然语言句） | 后端分词 + 食物库模糊匹配 + 数量单位提取 → 未能解析时才降级到文本模型 | 0 ~ 0.0004 元 | P0 |
| 语音 | 端上微信同声传译插件转文字（免费）→ 复用文字链路 | 同上 | P1 |
| 图片 | 后端调用 Qwen3-VL-Flash，要求输出结构化 JSON | 约 0.0006 元 | P1 |

**注意文字解析的分层设计**：先用零成本的规则方案（分词 + 模糊匹配 + 单位提取）处理"两个鸡蛋、一碗米饭"这类结构化程度高的输入，只有规则失败时才调用大模型。实测中大部分日常输入都能被规则覆盖，这能把文字录入的边际成本压到接近零。

### 5.3 模型选型

- 图片识别：Qwen3-VL-Flash（输入 0.15 元/百万 token、输出 1.5 元/百万 token，缓存命中 0.03 元/百万 token）。要求返回结构化 JSON，含食物名、估算份量、置信度。
- 文本兜底解析：同厂商的轻量文本模型。
- **建议文案生成：不用 AI，用模板。** 推荐理由的表达完全可以由模板拼装（见 04 文档），零成本且输出稳定。后续如需更自然的表达再考虑接入。

### 5.4 降本措施（从第一天就要做进架构）

1. 图片上传前压缩至短边 512px —— token 量与分辨率是平方关系，这是最有效的降本杠杆。
2. 启用 prompt 缓存，系统提示词部分可享受约 80% 折扣。
3. 相同图片指纹 / 相同文本输入的解析结果缓存复用。
4. 免费用户每日 AI 调用配额限制（云端计数，不可放本地）。
5. 高频食物本地命中，不走云端解析。

## 6. 部署方案

### 6.1 进程与端口

FastAPI 服务以独立进程运行（`uvicorn` + `gunicorn` worker，或容器化），监听本机端口（如 `127.0.0.1:8100`），不直接暴露公网。

### 6.2 Nginx 分流

在现有域名下按路径前缀分流，避免申请新域名与重新备案：

```nginx
location /api/health/ {
    proxy_pass http://127.0.0.1:8100/;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_read_timeout 30s;   # AI 调用可能较慢
}
```

小程序后台需将该域名加入 `request` 合法域名列表。

### 6.3 资源隔离

由于与现有业务共用服务器，必须设置资源上限，避免本项目的 AI 调用阻塞或拖垮现有业务：

- 限制 worker 数量与连接池大小
- 所有外部 AI 调用设置超时（建议 15 秒）与熔断
- 独立的日志文件与轮转策略
- 数据库连接池独立且限额

### 6.4 环境划分

至少区分 `dev` 与 `prod` 两套配置，通过环境变量注入。AI Key、数据库密码、微信 AppSecret 全部走环境变量，不进代码仓库。

## 8. 安全要点

1. 微信登录：小程序 `wx.login` 拿 code → 后端用 AppSecret 调 `code2Session` 换 openid，签发自有 JWT。AppSecret 只存服务端。
2. 所有接口强制鉴权，用户只能访问自己的数据（在 repository 层强制注入 `user_id` 过滤，不依赖调用方传参）。
3. 图片上传：限制大小与格式，服务端二次校验，不信任客户端声明的 MIME。
4. 接口限流：按用户与 IP 双维度，防止 AI 接口被刷产生费用。
5. 敏感数据：健康数据属于个人敏感信息，传输强制 HTTPS，数据库层面做好访问控制与定期备份。
6. 隐私政策与用户协议在首次启动时明示并获取同意，说明数据存储位置与用途。
