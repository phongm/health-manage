# 01 · 产品定义

## 1. 一句话定位

**给减脂人群的饮食决策助手**：根据你的身体数据、今日已摄入、运动消耗和历史饮食习惯，告诉你「下一餐吃什么」，以及「今天要避开什么」。

## 2. 为什么这个定位成立

### 2.1 与竞品的关系

头部竞品的护城河建在**记录侧**：薄荷健康拥有约 160 万条食物数据、2 亿累计注册用户，并用用户饮食大数据训练识别模型；蚂蚁阿福有 1 亿用户，并已于 2026 年接入薄荷数据库提供免费的拍照记卡路里。

在"食物数据库规模"和"图片识别精度"上正面竞争没有胜算。但**推荐侧**依赖的是规则设计与个性化逻辑，不依赖数据规模，是可竞争的战场。

### 2.2 用户价值逻辑

记录类产品的根本问题：它要求用户付出成本（每天记录），却把收益（分析结果）留给用户自己解读。用户流失的原因不是产品不好，而是**记录本身没有即时回报**。

本产品把因果关系反过来：
- 记录 → 立刻得到「下一餐吃什么」的具体答案
- 记录越多 → 推荐越贴合口味
- 记录成为获取推荐的手段，而不是目的

这也是本产品必须遵守的第一设计原则：**任何时刻，记录行为都必须换来一个立即可见的推荐结果。**

## 3. 目标人群

### 3.1 核心人群

统一目标为**减脂/体重管理**，按就餐场景分为三类：

| 场景 | 特征 | 推荐形态 |
| --- | --- | --- |
| **A · 外卖党** | 不做饭，每餐面临外卖平台的选择困难 | 推荐"点什么菜品"，给出可在外卖平台搜索的菜名与避坑提示 |
| **B · 食堂党** | 公司/学校食堂，可选范围有限但固定 | 推荐"怎么打菜"，主食+荤菜+素菜的组合与分量 |
| **C · 自己做饭** | 有条件下厨 | 推荐"做什么菜"，给出食材组合与简单做法 |

场景由用户在引导流程中设置，可随时切换，也可按餐次分别设置（如午餐吃食堂、晚餐自己做）。

### 3.2 明确排除人群

以下人群在引导流程中识别并劝退，不提供推荐服务（仅保留基础记录功能）：

- 糖尿病、高血压、肾病等慢性病人群
- 孕期、哺乳期女性
- 18 岁以下未成年人
- BMI < 18.5 的低体重人群（不提供减脂方案）
- 有进食障碍史的人群

排除原因是合规而非技术：涉及疾病人群的饮食干预属于医疗建议范畴。

## 4. 核心功能

### 4.1 P0 — MVP 必须有（第 1-10 周）

| 功能 | 说明 |
| --- | --- |
| 基础信息与目标设定 | 身高、体重、年龄、性别、活动水平、目标减重速率；计算 BMR/TDEE/每日目标热量与三大宏量营养素目标 |
| 偏好与忌口设置 | 过敏原、忌口食材、不吃的肉类、辣度偏好、就餐场景 —— **这是冷启动推荐质量的关键输入** |
| 文字录入 | 食物搜索 + 常见份量快选（一碗/一份/中份），而非要求输入克数 |
| 每日能量收支看板 | 目标 / 已摄入 / 运动消耗 / 剩余额度，以及三大宏量营养素进度 |
| **餐次推荐** | 核心功能。按剩余额度与营养缺口推荐下一餐组合 |
| **换一换** | 在同一"营养生态位"内替换，替换后仍满足营养目标；同时作为负反馈信号 |
| **今日避雷清单** | 基于目标与今日已摄入，列出今天应避开的食物类型及原因 |
| 体重记录与趋势 | 折线图 + 周均值（周均值比单日体重更有意义） |
| 运动录入 | 运动类型 + 时长 + 强度，按 MET 公式计算消耗 |

### 4.2 P1 — 增强（第 11-20 周）

- 语音录入（微信同声传译插件转文字后复用文字解析链路）
- 图片识别录入
- 周报：营养达成率、体重趋势、饮食结构分析
- 食物库 UGC 共建（扫码 + 拍营养成分表）
- 多日食谱规划（付费功能候选）

### 4.3 P2 — 后续

- 膳食纤维与主要微量元素统计
- 付费会员与虚拟支付接入
- 数据导出
- 多端扩展

### 4.4 明确不做

社区、社交、动态、打卡排行、直播、人工营养师咨询、智能硬件对接、内容资讯。

理由：单人兼职开发（约 20 小时/周）的产能极其有限，任何非核心功能都会挤压推荐引擎的打磨时间，而推荐质量是本产品唯一的竞争力来源。

## 5. 核心用户旅程

### 5.1 首次使用（目标：90 秒内看到第一个推荐）

```
授权登录
  → 基础信息 6 项（身高/体重/年龄/性别/活动水平/目标速率）
  → 立即展示「你的每日目标热量与营养目标」
  → 偏好问卷 30 秒（忌口/过敏/不吃的肉/辣度/就餐场景）
  → 立即给出「下一餐推荐」  ← 此处必须成功，是留存的决定性节点
  → 引导记录第一餐
```

**关键设计**：推荐在**零历史数据**时就必须可用（见 04 文档冷启动方案）。绝不能出现"记录几天后才能获得推荐"的设计——那样用户在拿到价值前就流失了。

### 5.2 日常主循环

```
打开小程序
  → 首屏直接显示：剩余额度 + 下一餐推荐
  → 采纳推荐 / 换一换
  → 吃完后一键记录（从推荐直接转记录，无需重新搜索）
  → 看到更新后的剩余额度与下一餐推荐
```

**关键设计**：从推荐到记录必须是**一键完成**的。用户既然采纳了推荐，就不该再让他手动搜索录入一遍。这一步能大幅降低记录摩擦，同时保证数据质量。

## 6. 成功指标

MVP 阶段只看留存，不看收入：

| 指标 | 及格线 | 说明 |
| --- | --- | --- |
| 次日留存 | ≥ 30% | 低于此说明首次体验有问题 |
| 7 日留存 | ≥ 15% | **核心门槛**。低于此不要继续加功能，回头重做推荐质量与录入流程 |
| 记录满 7 天用户占比 | ≥ 20% | 衡量习惯养成 |
| 推荐采纳率 | ≥ 40% | 衡量推荐质量。采纳 = 推荐被直接转为记录 |
| 换一换次数/推荐次数 | ≤ 1.5 | 过高说明首推质量差 |

变现验证放在 7 日留存达标之后（详见 06 文档）。
