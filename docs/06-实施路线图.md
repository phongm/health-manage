# 06 · 实施路线图

产能假设：**约 20 小时/周**（兼职）。所有排期基于此，不做乐观估计。

## 1. 第 0 周 · 立刻要做的前置事项

这些事有外部审核周期，越早启动越好，且它们不消耗你的开发时间：

1. **小程序 ICP 备案**（有审核周期，是上线前置条件）
2. **服务类目申报**：选「工具 - 健康管理」，无需资质。备案时的服务内容标识同样选此项
3. **域名加入小程序 request 合法域名列表**
4. **并行询价**：唤醒食物（`foodwake.cn`）与 NutriData（中营华堂）的数据授权报价 —— 若报价可接受，可直接省掉第 3-4 周的大部分食物库整理工作
5. 起草隐私政策与用户协议（含健康数据说明与免责声明）

## 2. Phase 1 · MVP（第 1-10 周，约 200 小时）

目标：完成「设置目标 → 得到推荐 → 一键记录 → 看到剩余额度」的完整闭环并上线。

### 第 1-2 周（40h）· 骨架与用户体系

- FastAPI 项目骨架、配置管理、异常处理、日志
- PostgreSQL 独立 database、Alembic 迁移、users / user_profiles / user_preferences
- 微信登录（`code2Session` → JWT）
- `/profile`、`/preferences` 接口
- `core/nutrition` 纯 TS 包：BMR / TDEE / 目标热量 / 营养目标（含三重安全边界）+ 单元测试
- 小程序骨架、分包结构、请求封装、引导流程页面（6 项基础信息 + 偏好问卷）

**里程碑**：新用户能完成引导并看到自己的每日目标热量。

### 第 3-4 周（40h）· 食物库与录入

- 食物库建设（见第 5 节，这是本阶段最大的工作量）
- `foods` / `food_portions` 表与导入脚本
- `/foods/search`、`/foods/hot` 接口
- 端上本地食物缓存（分片 storage 抽象层 + 容量守卫）
- 文字录入页：搜索 → 选份量 → 确认
- `/intake` 写入与 `/dashboard` 看板接口
- 今日看板页面

**里程碑**：能完成"搜索食物 → 记录 → 看到今日剩余额度"。

### 第 5-7 周（60h）· 推荐引擎 ← 投入最多的部分

- Layer 0-1：目标与缺口计算（含按剩余餐次动态分配）
- Layer 2：避雷规则引擎 + `avoid_rules` 表 + MVP 规则集（9 条）
- Layer 3：按角色与场景召回（硬排除下沉到 SQL）
- Layer 4-5：打分与组合生成（蛋白优先贪心）
- Layer 6：份量档位微调
- Layer 7：模板文案生成
- `/recommend`、`/avoid-list` 接口
- 推荐页面 + 一键转记录
- **单元测试**：营养计算、安全下限、过敏原过滤、额度校验（见 04 文档第 13 节）

**里程碑**：零历史数据的新用户也能得到可执行的一餐推荐。这是整个项目的核心验证点。

### 第 8-9 周（40h）· 换一换、体重与避雷清单

- 换一换（营养生态位替换 + 三类原因区分）
- `recommendation_feedback` 与 `user_food_affinity` 更新逻辑
- 体重记录与趋势图（7 日移动平均）
- 避雷清单页面
- `/sync` 增量同步与待同步队列
- 埋点（留存、采纳率、换一换率）

**里程碑**：核心闭环完整，可交付内测。

### 第 10 周（20h）· 上线

- 隐私政策与用户协议接入
- 全站文案合规审查（禁用词检查：检测/诊断/预警/治疗/缺乏症）
- 提审与审核问题修复

### 2.1 排期偏紧的应对：可砍项

上述排期是**紧的**。如果进度落后，按以下顺序砍：

1. **每日运动录入 → 砍掉，只保留 profile 中的活动水平设置。** 省约 12h。理由：运动消耗估算误差大且只按 70% 计入，对推荐结果影响有限；而它需要运动库、录入页、MET 计算三块工作。
2. **体重趋势图 → 简化为列表 + 最近变化值。** 省约 6h。
3. **避雷清单独立页 → 合并进推荐页的一个折叠区块。** 省约 5h。

**绝不能砍的**：推荐引擎的安全边界、过敏原硬过滤、偏好问卷（冷启动的关键）、单元测试。

## 3. Phase 2 · 留存验证（第 11-24 周）

**这个阶段的唯一目标是把 7 日留存做到 15% 以上。在达标前不要做变现，也不要加新功能维度。**

- 第 11-13 周：语音录入（微信同声传译插件 → 复用文字解析链路）
- 第 14-16 周：图片识别（Qwen3-VL-Flash）+ 置信度确认交互
- 第 17-19 周：推荐算法调优（依据采纳率与换一换率调整权重）、食物库扩充与场景标签修正
- 第 20-22 周：周报、TDEE 自校准（L4）
- 第 23-24 周：食物库 UGC 共建（扫码 + 拍营养成分表）

**决策关卡（第 24 周）**：
- 7 日留存 ≥ 15% → 进入 Phase 3
- 7 日留存 < 15% → **不要进入变现阶段**。回到推荐质量与录入流程做重构，重点分析换一换原因分布与流失节点

种子用户获取：减脂社群、小红书、朋友圈。规模 100-500 人足够验证留存，不要过早追量 —— 在推荐质量未打磨好时导入大量用户，等于浪费获客机会。

## 4. Phase 3 · 变现验证（第 25-36 周）

前置条件：留存达标。

- 开通**独立的虚拟支付商户号**（不可与普通商户号混用）
- 接入 `wx.requestVirtualPayment`
- iOS 端额外配置「小程序简称」，注意 **iOS 端不支持沙箱环境**，必须用现网真实扣款测试（最低 1 元）
- 付费点：多日食谱规划、换一换不限次、个性化避雷深度 —— **不要把图片识别设为付费墙**
- 费率预期：iOS 端 12%（2026 年，Apple 12% + 腾讯 5% 限时减免为 0；标准费率 17%），Android/鸿蒙/Windows 约 1%
- 注意 Apple 支付**开发者无法主动退款**，需在产品设计上做好购买前的说明

**决策关卡**：付费转化率 ≥ 1%。

定价建议年费优先于月费：iOS 端每次扣费都要被抽成 12%，且月费的续费流失率更高。

## 5. 食物库建设计划（最大的隐性工作量）

MVP 需要约 700-1000 条食物。如果逐条手工查营养数据，工作量会超过 100 小时，远超预算。因此必须用**配方分解法**。

### 5.1 配方分解法

只精确维护 **150-200 条基础食材**的营养数据，复合菜品（占食物库的大头）通过配方自动计算营养：

```
清蒸鸡胸 = 鸡胸肉 120g + 植物油 2g + 生抽 5g
  → 营养值由基础食材按重量加总自动生成
```

建议在 03 文档的数据模型中补充一张表：

```sql
CREATE TABLE food_recipes (
    id            BIGSERIAL PRIMARY KEY,
    dish_food_id  BIGINT NOT NULL REFERENCES foods(id) ON DELETE CASCADE,
    ingredient_id BIGINT NOT NULL REFERENCES foods(id),
    grams         NUMERIC(7,1) NOT NULL,
    note          VARCHAR(64)
);
```

`foods.nutrients` 对复合菜品由脚本按配方计算后写入（物化存储，不实时算，避免查询开销）。配方变更时重跑脚本。

这个方法的三个收益：
1. 工作量从"逐条查 800 道菜"变成"精确 200 条食材 + 快速配比 600 道菜"，节省约 50-60 小时
2. 基础食材数据修正后，所有相关菜品自动更新
3. 天然支持"家常菜做法"展示（配方本身就是食材清单），直接服务场景 C

### 5.2 数据来源与合规

| 类型 | 来源 | `source` 值 | 合规性 |
| --- | --- | --- | --- |
| 基础食材 | USDA FoodData Central（公开 API，免费）+ 中文名映射 | `usda` | 安全 |
| 预包装食品 | 采集包装上依 GB 28050 强制标注的营养成分表 | `label` | 安全（产品标识信息） |
| 复合菜品 | 由基础食材配方计算 | `self_built` | 安全 |
| 用户共建 | UGC 扫码 + 拍营养表，经审核 | `ugc` | 安全 |
| 商业授权 | 若购买唤醒食物 / NutriData | `licensed` | 安全 |

⚠️ **明确禁止**：将《中国食物成分表》等有版权出版物的数据（包括网络上流传的 OCR 提取版本、GitHub 上的开源转换项目）导入生产库。该书版权归中国疾病预防控制中心营养与健康所，无开放 API，商业使用需授权。

### 5.3 分批建设顺序

按对推荐引擎的重要性排序，边建边可用：

1. **第一批（约 200 条，第 3 周）**：基础食材。主食 20、肉禽蛋 40、水产 20、豆制品 15、蔬菜 60、水果 25、乳品 12、油脂调味 10。这批必须**数据准确**，因为后续所有菜品依赖它
2. **第二批（约 250 条，第 4 周）**：三场景核心菜品。外卖常见 100、食堂常见 80、家常菜 70。用配方分解法快速生成
3. **第三批（约 150 条，第 8-9 周）**：零食、饮料、快餐 —— 这批主要服务**避雷功能和记录完整性**，不用于推荐
4. **第四批（持续）**：UGC 共建的预包装食品

### 5.4 标注质量要求

`role_tags` 与 `scene_tags` 的准确性直接决定推荐能否执行（见 04 文档 5.2）：

- `role_tags` 不得留空，否则该食物永远不会被组合推荐召回
- `scene_tags` **宁可标少不要标错**。标少只是候选池变小，标错会推荐出用户买不到的东西，直接损伤信任
- 每条食物至少配置 2 个 `food_portions` 档位，且必有一个默认值
- 上线后通过换一换的 `not_available` 原因统计反向修正场景标签

## 6. Phase 4 · 多端扩展（第 37 周以后）

仅在前三阶段验证通过后启动。届时复用 `core/` 纯 TS 包，重写 UI 层。

**具体技术路线（Flutter / React Native / 各端原生）建议推迟到第 36 周再决策**，因为届时的框架生态、鸿蒙市场份额与你的实际资源都与今天不同，现在做这个决定没有信息基础。

## 7. 成本预算

基于已核实的定价（Qwen3-VL-Flash 输入 0.15 元/百万 token、输出 1.5 元/百万 token）与推算的单次调用成本（图片约 0.0006 元）：

| 阶段 | 用户规模 | AI 成本 | 服务器 | 合计（月） |
| --- | --- | --- | --- | --- |
| MVP 内测 | < 500 | < 10 元 | 复用现有 | **< 10 元** |
| 增长期 | 1 万 MAU | ~300 元 | 复用现有（可能需扩容） | **约 300-500 元** |
| 规模期 | 10 万 MAU | ~3000 元 | 需独立服务器 | **约 4000 元** |

复用现有服务器让 MVP 阶段的边际成本几乎为零，这是本项目能长期低成本存活的基础。

降本措施（第一天就做进架构）：图片压缩至短边 512px、prompt 缓存、解析结果缓存、文字优先走零成本规则解析、免费用户每日配额限制。

## 8. 主要风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| **推荐不可执行**（推荐了买不到/做不了的东西） | 直接失去信任，最致命 | 严格的 `scene_tags` 标注纪律；上线后用 `not_available` 反馈持续修正 |
| **冷启动推荐质量差** | 新用户在拿到价值前流失 | 偏好问卷（L1）必须进 MVP；零数据也能出可用推荐 |
| **食物库建设超时** | 挤压推荐引擎的开发时间 | 配方分解法；分批建设；必要时购买商业授权 |
| **巨头竞争**（蚂蚁阿福免费提供拍照记热量，已接入薄荷数据库） | 记录侧无法竞争 | 不在记录侧竞争，全部资源投入推荐侧 |
| **产能不足导致排期崩溃** | MVP 迟迟不上线 | 严格执行第 2.1 节的可砍项；不做社区等非核心功能 |
| **合规措辞违规** | 类目审核不通过或被处罚 | 全程只用"记录/统计/参考"；排除人群在数据层留痕；上线前全站禁用词检查 |
| **AI 接口被刷产生费用** | 意外账单 | 云端配额计数 + 双维度限流 + 供应商侧设置消费上限 |
