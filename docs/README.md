## 关键决策记录（ADR）

记录已确定的决策及其理由，避免后续反复推翻。

| # | 决策 | 结论 | 理由 |
| --- | --- | --- | --- |
| 1 | 产品定位 | 饮食**决策助手**，而非记录工具 | 记录是用户成本，推荐是用户收益；且推荐侧是头部竞品的弱项 |
| 2 | 目标人群 | 减脂人群，覆盖三种就餐场景：外卖 / 食堂 / 自己做饭 | 目标统一、场景分化，推荐策略可按场景切分 |
| 3 | 明确排除人群 | 慢病（糖尿病/高血压/肾病等）、孕产期、哺乳期、未成年人 | 规避医疗建议合规红线 |
| 4 | 数据存储 | **云端为真相源 + 本地缓存加速** | 推荐引擎依赖长期历史数据；小程序本地缓存会被微信随代码包清理，不可作为唯一存储 |
| 5 | 后端技术栈 | Python + FastAPI，独立服务，复用现有服务器与已备案域名 | 已有服务器和备案域名，省去备案周期与额外成本 |
| 6 | 数据库 | PostgreSQL（复用现有实例，独立 schema/database） | 已有；JSONB 适合存营养素向量 |
| 7 | 小程序端 | 原生小程序 + TypeScript | 单端最快；业务逻辑抽为纯 TS 核心包，为多端预留 |
| 8 | 营养数据库 | 自建精简库（约 700-1000 条）+ UGC 共建 | 规避《中国食物成分表》版权风险；UGC 库是可积累的资产 |
| 8b | 食物库建设方式 | **配方分解法**：精确维护约 200 条基础食材，复合菜品由配方自动计算 | 把工作量从"逐条查 800 道菜"降到可承受范围，节省约 50-60 小时 |
| 9 | AI 分工 | AI 只做"翻译"和"表达"，绝不做"判断" | 判断全部交由确定性规则引擎，保证可解释、可复现、合规、零边际成本 |
| 10 | MVP 录入方式 | 文字为主，语音（微信同声传译插件，免费）为辅 | 图片识别延后；语音信息完整度高于图片且成本更低 |
| 11 | 付费点 | 推荐深度（多日规划、换一换次数、个性化避雷），**不把图片识别设为付费墙** | 录入越顺畅，历史数据越多，推荐越准；在录入环节设墙等于自断数据来源 |
| 12 | 小程序类目 | 「工具-健康管理」（无需资质） | 全程使用"记录/统计/参考"措辞，避免触发「其他医学健康服务」的资质要求 |

## 待确认事项

| # | 事项 | 影响 |

| 1 | 现有服务器上的 Python 框架与版本 | 若为 Django 且希望合并部署，需调整接入层方案（见 02 文档） |

| 4 | 是否已有可复用的用户体系 | 若现有小程序已有用户表，需决定是否共用 |

## 合规红线（开发全程遵守）

1. 文案只使用「记录」「统计」「参考」「建议」，禁止使用「检测」「诊断」「预警」「治疗」「缺乏症」。
2. 所有建议类输出附带免责声明，并提示特殊人群咨询专业人士。
3. 不针对任何疾病提供饮食干预方案。
4. 能量建议设置安全下限（见 04 文档 Layer 0），不得输出极端节食方案。
5. AI 生成内容不得直接作为健康结论输出，必须经规则引擎校验。
